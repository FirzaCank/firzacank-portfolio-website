## Context

A self-initiated learning project to practice the full ML lifecycle on a single, well-known business problem: predicting subscriber churn for a telecom company. The dataset is dummy data published by DQLab for a fictional company called DQLab Telco, modeling customer state as of June 2020 with around 6,800 rows and 21 attributes covering demographics, services subscribed, contract type, and billing.

The goal was not just to fit a model. It was to make the analysis legible end-to-end: someone landing on the live app should be able to walk through cleansing, EDA, model comparison, and finally type in customer attributes and get a churn probability back.

## Problem

The business framing on the cover page sets it up: DQLab Telco wants to reduce the number of customers who churn by using machine learning to predict, ahead of time, who is likely to unsubscribe. From a modeling standpoint that translates into three concrete constraints:

- The target class is imbalanced (around 26% churn, 74% non-churn), so accuracy alone is misleading.
- Most predictors are categorical (gender, partner status, service flags, contract terms), which means encoding choices matter.
- The output has to be usable. A score in a notebook does not help operations; a form that takes ten inputs and returns a churn probability does.

## Approach

The Streamlit app is split into four navigable sections, each one mapping to a stage of the pipeline.

**Data cleansing.** Drop the operational columns (customerID, UpdatedAt), handle missing TotalCharges, and standardize types. The cleaned dataset is exported to a separate CSV so EDA and modeling can both read from the same canonical source.

**Exploratory data analysis.** Bivariate plots against the Churn label for both numerical and categorical features. The numerical view uses overlaid histograms, the categorical view uses seaborn count plots, and the overall churn ratio is shown as a Plotly donut. Three findings shaped how I framed the model output later:

- Higher monthly charges correlate with higher churn.
- Longer tenure correlates with lower churn.
- StreamingTV, InternetService, and PaperlessBilling users churn at higher rates than their counterparts, suggesting service quality or pricing friction in those segments.

**Model building.** Label encode all non-numeric columns, split 70/30 with a fixed random state, then fit three baseline classifiers with default hyperparameters:

- Logistic Regression
- Random Forest Classifier
- Gradient Boosting Classifier

Each model has its own classification report and confusion matrix surfaced in the app, with separate views for the training and testing splits so the over-fit pattern is visible.

**Prediction.** A form takes ten attributes (gender, senior citizen, partner, tenure, phone, streaming TV, internet, paperless billing, monthly charges, total charges), encodes them the same way the training pipeline did, and pushes them through a pickled model loaded via joblib. The app returns the predicted class plus the probability for both outcomes.

## Results

Test-set accuracy across the three baselines came out close, but the training accuracy told the real story:

- **Logistic Regression: 80% train / 79% test.** Balanced and generalizes cleanly.
- **Random Forest: 100% train / 78% test.** Classic overfit signal.
- **Gradient Boosting: 82% train / 79% test.** Slightly better train fit than Logistic Regression, no meaningful test gain.

I selected **Logistic Regression** as the production model precisely because the gap between train and test accuracy was the smallest. The confusion matrix on the test set shows the model is more conservative on positive predictions than on negatives, which is appropriate when the downstream action (retention offers, discount budget) has a cost per customer that you do not want to spray indiscriminately.

The takeaway I wrote into the Conclusion section of the app is the operational one: an ML score lets the company concentrate retention spend on the slice of customers actually predicted to churn, instead of running blanket promotions across the full base.

## Stack notes

- **Streamlit** for the entire UI. No Flask, no React layer. The same script that runs locally is what gets deployed to share.streamlit.io.
- **scikit-learn** for all three models. Keeping the API uniform across LR, RF, and GBC made the side-by-side comparison straightforward.
- **joblib** for model persistence inside the app, **pickle** for the saved artifact in the repo.
- **Plotly + matplotlib + seaborn** mixed deliberately. Plotly handles the interactive churn donut, matplotlib renders the confusion matrices, seaborn does the categorical count plots.

The full source, including the cleansing, EDA, and ML modules as separate Python files, is on GitHub at [FirzaCank/Churn](https://github.com/FirzaCank/Churn).
